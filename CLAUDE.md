# Kvitka Centrum website

## Project overview

A website for **Kvitka Centrum**, a beauty salon (lashes, massage, keratin treatments, haircuts, nails, waxing) in Enschede, Netherlands. Started as a generic single-page "barbershop pitch" template and was rebranded into a real site for this client.

- **Stack**: Next.js (App Router) + TypeScript + Tailwind CSS, no database/auth.
- **Live site**: https://kvitka-centrum-salon-aldb.vercel.app
- **GitHub**: https://github.com/AlmarvDiessen/KvitkaSite
- **Vercel project**: `kvitka-centrum-salon` (Vercel team: `aldb`)
- **Run/deploy/edit instructions**: see `README.md` — this file is status and history, not a how-to.

## Branching workflow

- `main` — stable/production. **Protected**: direct pushes are rejected by a GitHub repository rule; all changes land via a reviewed, merged pull request.
- `develop` — integration branch, branched from `main`. Feature work merges here first.
- `feature-<branch-name>` — one branch per piece of work, branched from `develop` (e.g. `feature-real-prices`, `feature-calendar-setup`). Open a PR into `develop` when ready; `develop` gets merged into `main` periodically once it's in a good state.

### Vercel deployments

Only `develop`/`main` should ever have a lasting deployment — the Vercel dashboard isn't git-integrated, so nothing deploys automatically; every deployment is a deliberate CLI run. For feature branches: deploy a **preview** (`vercel`, no `--prod`) to test live, delete it once confirmed good (`vercel remove <url> --yes`), then it's ready to merge into `develop`. Production itself only gets redeployed deliberately, not on every merge.

**Production deploys MUST go through `npm run deploy` (never a raw `vercel --prod`).** That script (`deploy.sh`) checks the current git branch and refuses to run unless it's exactly `develop` or `main` — this isn't just a documented rule, it's enforced in the one shared deploy path, after a recurring problem where ad-hoc `vercel --prod` runs from whatever branch happened to be checked out piled up 20+ stray deployments on the dashboard. If you ever need to bypass this deliberately, that's a sign to stop and reconsider, not to run the raw `vercel` command instead.

`deploy.sh` also fetches and compares the local branch against `origin` before building, refusing to deploy if they don't match exactly. Being on a branch *named* `develop`/`main` isn't sufficient on its own — a stale local checkout that hasn't pulled recent merges would otherwise pass the name check and silently redeploy old code over newer production content (this happened: see 2026-11-11 below).

The one practical wrinkle this creates: a git **worktree** can't check out a branch name that's already checked out elsewhere (e.g. in the main clone). A worktree sitting on a differently-named branch — even with identical, up-to-date content via `git reset --hard origin/develop` — will still be refused by the branch-name check, since the check is on the literal ref name, not content equality. Deploy from whichever checkout actually has `develop`/`main` checked out by name.
